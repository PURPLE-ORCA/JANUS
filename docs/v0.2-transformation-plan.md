## Executive Summary

JANUS v0.1 delivered a visually stunning recruitment platform UI, but with an insufficient data model. Before wiring the backend, we must extend the database schema to match industry standards (Indeed, ReKrute.com, Emploi.ma).

**The Problem**: Our current schema is missing 60% of fields that recruiters expect:

- No company entity (jobs appear orphaned)
- No education/experience history for candidates
- No screener questions for job applications
- No recruiter notes system
- Missing Morocco-specific fields (languages, Bac+X education levels)

**The Solution**: A 3-stage transformation that extends the data model while preserving the existing UI.

## Why This Transformation?

### The Competitive Gap

| Feature                 | Indeed | ReKrute | JANUS v0.1 | JANUS v0.2 |
| ----------------------- | ------ | ------- | ---------- | ---------- |
| Company profiles        | ✅     | ✅      | ❌         | ✅         |
| Candidate work history  | ✅     | ✅      | ❌         | ✅         |
| Candidate education     | ✅     | ✅      | ❌         | ✅         |
| Language proficiencies  | ✅     | ✅      | ❌         | ✅         |
| Screener questions      | ✅     | ✅      | ❌         | ✅         |
| Recruiter notes         | ✅     | ✅      | ❌         | ✅         |
| Experience level filter | ✅     | ✅      | ❌         | ✅         |
| Morocco Bac+X levels    | N/A    | ✅      | ❌         | ✅         |

### What Happens If We Skip This?

If we wire the backend without this transformation:

1. **Job cards look empty** — No company logo or name
2. **Candidate profiles are shallow** — Just skills, no history
3. **Recruiters can't pre-screen** — No way to filter by experience/education
4. **No audit trail** — No notes on why candidates were rejected
5. **Missing local context** — Moroccan recruiters expect specific fields

## Stage 1: Backend Schema

### Why This Stage First?

- **Migrations are the source of truth** — Everything else (types, forms) derives from the database schema
- **Laravel's type safety** — Eloquent models provide the relationships we need
- **Easy rollback** — If something breaks, `migrate:rollback` fixes it

> [!IMPORTANT]
> **Development Approach**: Since we're not in production, we'll:
>
> - **Edit the existing `create_users_table` migration** to add JANUS columns directly
> - **Create new migration files** for new tables (companies, profiles, etc.)
> - **Run `migrate:fresh`** to rebuild the database from scratch
>
> This is cleaner than creating separate "alter table" migrations.

### 1.1 Migrations

#### Migration 1: Modify existing users table

**File**: `0001_01_01_000000_create_users_table.php` (EDIT EXISTING)

**Purpose**: Add JANUS columns directly to the users table creation

**Add these columns**:

- `role` — enum('admin', 'candidate'), default 'candidate'
- `status` — enum('pending', 'active', 'rejected'), default 'pending'
- `avatar_path` — nullable string

**Why**:

- New signups are `pending` until admin approves
- Role determines dashboard view (candidate vs admin)
- Avatar for personalization
